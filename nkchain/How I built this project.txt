I built this project in three parts/phases.

The mvp is the most difficult part of the three parts of the project to build.

Part one was just the mvp and was built in nine stages.

Stage four is the most important stage of part one and arguably maybe the most important aspect of all three parts of the project. 

This was the stage where nkchain stopped being a basic wallet CRUD app and it started becoming a real financial ledger system.

nkchain uses two databases. the first one is the main database for the normal application. the second database is simply a test database for testing the ledger without actually modifying anything.

26/09/2026:
For the duration of each transaction, an exclusive lock on the sender's wallet record is held by PostgreSQL.

The ".with_for_updates()" function in the "app/services/ledger_service.py" file is what makes this happen. 

The whole point of this is to protect the system against concurrent double spend attempts that can happen at the same exact microsecond.


I've also added a Transaction State Machine so that the transactions don't continue instantly defaulting to COMPLETED like they used to do. 

Hopefully, this allows the transactions to progress through explicit lifecycle states to handle asynchronous processing, confirmations and failure recoveries safely.

There are four transaction statuses that I created. they can be more than four, but for now, I'll stick with four. They are: PENDING, COMPLETED, FAILED and REVERSED.

These are what they mean:

PENDING: Transaction has been initiated, waiting for validation or execution.   

COMPLETED: Debit entries and credit entries have been successfully posted.   

FAILED: Transaction has been aborted due to validation errors or maybe system issues.   

REVERSED: Transaction has been rolled back or maybe it has been refunded.


Yes, in this system, transactions should be able to be refunded.
